它是什么，以及为什么值得看

它是什么

DeepSeek 开源的 agent harness（智能体框架），命令行叫 dsh。你会得到一个能读写文件、跑命令、委派子 agent、维护计划的编码智能体 —— 但重点不是"又一个编码 agent"。

它的赌注

这套壳子本身可以整块替换。模型适配器、工具注册表、会话日志、沙箱策略，甚至 agent loop 本身，全都是插件 —— 于是每一部分都能从配置替换掉。

底座

以 vendor 方式引入的插件框架 Cordis，其设计出自论文《A Programming Paradigm for Spatiotemporal Composability》。插件向共享上下文贡献服务、类型化事件与可逆的副作用。

问题定义

为什么要把 harness 拆成插件树

大多数 agent 产品有一个"特权内核"：循环、工具、上下文管理写死在一起。想改行为，要么 fork，要么打补丁，要么等上游合 PR。dsh 用另一条路线回答这件事。

单体内核

  • 扩展 = fork 仓库 / monkey patch / 等待上游
  • 能力写死在循环里，加一个工具要动主流程
  • 换执行环境（远程沙箱）要为每个提供方做专用 fork
  • 卸载一个功能没有明确边界，残留状态靠人记

dsh 的插件树

  • 扩展 = 把插件挂到别的插件旁边，不碰任何核心
  • 每一项注册都是可撤销的副作用，卸载即还原
  • 换一个服务提供方，整条能力链一起搬走
  • 加载顺序由服务依赖推导，不需要手写启动序列
不存在需要打补丁的特权内核：扩展 dsh 的方式是把插件挂载到其他插件旁边，而各项注册都是副作用，会在其插件卸载时撤销。 docs/architecture.zh.md
代价先说在前面：把编译期的确定性换成了配置期的组合自由。这笔账靠一整套工程纪律来平（第 22 页）。
底座 · Cordis

五个核心概念，撑起整个架构

1

插件是实现 Service 的对象

可以是带可选 inject 和 apply(ctx) 的函数，也可以是 Service 子类，生命周期由 Cordis 挂载到当前上下文。

2

上下文是服务的容器

一个服务占据一个稳定的 ctx.<key>（ctx.tools、ctx.llm、ctx.sessions）。别的插件按 key 查找服务，而不是 import 具体实现 —— 这就是可替换性的来源。

3

用 inject 声明依赖

插件声明所需服务后，等这些服务就绪才启动。加载顺序通过服务依赖表达，而非手动编排启动序列。

4

类型化事件用于通信

服务通过 TypeScript 声明合并注册事件名，再以 emit / waterfall / parallel / serial 分发。

5

注册是可逆的副作用

提示词片段、工具 schema、模型适配器、服务提供方、事件监听器 —— 全部通过 ctx.effect() 或 ctx.on() 安装，reload 与 teardown 时按预期撤销。仓库规约写得很直白：Registrations are effects，注册表的 register() 必须返回 disposer。

第 5 条是前四条能成立的前提 —— 没有可逆性就没有热插拔，插件树只会变成越挂越脏的全局状态。
底座 · Cordis

四种分发模式，与 waterfall 的陷阱

模式await?分发顺序有返回值?
emit否按注册顺序观察否
waterfall否按注册顺序观察是
parallel是全部并行观察否
serial是按注册顺序观察是

waterfall = 环绕中间件

监听器收到 (...args, next)。调用 next() 执行下游，下游返回值回到当前包装层，可再包装后向外返回；不调用 next() 直接返回则短路。

对单决策事件，短路是设计意图：策略监听器拥有决策权时可以直接返回；而只做标注或观察的监听器必须委托。

最容易踩的坑

忘记调用 next() 就等于静默吞掉整条下游链 —— 工具流水线里少跑一层策略、提示词少一段、审批被跳过，全都不会报错。所以规约把它写成大写强制项：Waterfall listeners MUST call next()。

分发模式是事件公开约定的一部分。新事件用 @mode 标签记录模式，生成的目录会把声明和实际分发调用点做交叉校验 —— 声明和用法对不上，门禁直接挂。
运行时形态

跑起来的 dsh 是一棵插件树

没有"主程序 + 扩展点"这种二元结构。启动时按序叠加的各层组合出一棵树，树上的每个条目都是同一等级的公民。

这条命令就是心智模型

它打印出的任何条目，都可以由你自己的 patch 替换。包括 agent-loop。

行序不代表加载语义

激活由服务可用性驱动（谁 inject 了什么），YAML 里的顺序只是为了给人读。

HMR 是一等公民

cordis-plugin-hmr 在基础层里 —— 可逆副作用让插件热重载成为默认能力，而不是调试彩蛋。

组装机制

Profile 与 Bundle：五层叠加，按 id 覆盖

L0空条目列表一切从零开始
L1@deepseek-ai/dsh-base模型适配器 · 工具 · 持久化 · 沙箱与审批策略 · 设置 · 凭据 · 遥测
L2dsh-web-app 或 dsh-headless加浏览器应用；或加一次性运行器且完全不带服务器
L3profile/cordis.patch.yml这个 profile 自己的覆盖
L4$DSH_HOME/cordis.patch.yml整机级覆盖
L5--patch <overlay>本次启动的临时覆盖

patch 的语义：替换，不是深合并

一条 patch 按 id 定位条目，替换其整个 config，或插入新条目。所以"按模式取值不同"的行不会写在 base 里 —— 它属于各自的模式 bundle，让任何一行最多只经过"一个 bundle 层 + 用户层"。

两者都在 package.json 里自我声明

dsh.profile 列出一个 profile 叠放的组合包；dsh.bundle 指向一个组合包的 patch 文件。组合包 = 配置项 + 挂载代码的分发格式，所以它插入的内容始终可被上层 patch。

profile 是有状态的目录

存放在 Harness home，含 package.json（记录树外插件依赖）与 cordis.patch.yml。web 和 headless 首次使用自动初始化，其他 profile 必须用 dsh plugin 创建。

核心包

产品主干：七个包与它们的 ctx 键

包ctx 键职责
core/sessionctx.sessions仅追加的 SessionEvent 日志与内存存储 —— 模型所见上下文的唯一来源
core/system-promptctx.systemPrompt提示词片段与工具 schema 的组装
core/toolsctx.tools作用域化的工具注册表 + 带把关的执行流水线

llm/llmctx.llm消息与流式词汇表，以及适配器 seam

作用域：两级，扁平

一项贡献（工具 / 提示词片段 / 变量 / 限制 / 监听器）要么全局，要么归属恰好一个 scope。作用域注册不向下继承到 subagent —— 子树行为用 lineage 数据表达，不用 scope 结构。

遮蔽（shadowing）：最具体者胜

作用域内的同名工具/片段/变量，只在该 scope 内替换掉全局的同名孪生体。这正是"每个 agent 有自己的人设与工具变体"的实现机制。被限制过滤掉的全局工具，在提示词里消失、执行时也拒绝，与不存在无法区分。

扩展点

事件三域 —— 大多数改动的第一个决定

"事件就是扩展点，而选对事件域是大多数改动的第一个决定。"域选错了，功能能跑，但会在重载、fork、回放的某一天崩掉。

核心流程

轮次流程：一个 turn，零到多个 step

  1. turn/start
  2. 领取 next-step 输入 + 一条排队消息
  3. 组装提示词片段 + 工具 schema
  4. → agent/pre-step reject | enter(messages)
  5. 被拒 / 首次领取被改写为空 → 关闭一个不含 step 的轮次
  6. step/start
  7. 把 entered 消息追加为 user/message
  8. 从日志派生模型历史
  9. agent/request → llm/stream
  10. → assistant/chunk* → assistant/message
  11. tool/call* → tools/pre-execute
  12. → tools/execute → tools/post-execute
  13. → tool/result*
  14. step/end
  15. 工具还欠一次请求，或新输入到达 → 领取 → 下一 step
  16. → agent/turn-stopping （serial，无 next()）
  17. turn/end
持久会话事件 可回放 waterfall 监听器必须 next() 实时扩展点

两个定义

步骤 = 一次模型请求 + 它调用的工具。
轮次 = 零个或多个步骤：在领取首条输入之前打开，在不再欠下任何工作时关闭。

agent/pre-step 决定模型看到什么

监听器可以改写已领取的消息，也可以直接拒绝。即便被拒绝，仍然会关闭一个不含步骤的持久轮次 —— 于是日志里留下了"这次尝试发生过"的记录。

inbox 的两种消息

有些消息会立即唤醒驱动器；注入的上下文会留在 inbox 中，直到另一条消息把它唤醒。agent.inject() 就落在这条路径上。

核心不变量

模型可见 ⟺ 已记录

抵达模型请求的一切都必须能从日志重建 —— 并由一项运行时不变量断言这一点。 docs/architecture.zh.md · 会话日志

投影，而不是并行状态

deriveMessages() 从日志投影出模型历史；原始 assistant/chunk 事件保证回放与 UI 保真。没有第二份"真相"。

一切都派生自同一条流

fork、恢复、transcript、遥测、持久化 —— 全部派生自该事件流。所以"能不能 fork 一个会话"不是功能，是结构的推论。

它对开发者的约束

新增一项模型可见输入 = 新增一个会话事件：扩展 SessionEventMap，并从日志渲染。想偷偷塞点上下文给模型？门禁不让。

类型层面的强制

SessionEventMap 的成员默认是"读取时必需"：不认识这个类型的构建会拒绝这份日志，除非事件带上信封的 ignorable: true。只有结构性格式变更才会提升 SESSION_FORMAT_VERSION。

落到磁盘

持久化本身也是 seam：ctx.sessionPersistence 背后是 -jsonl 或 -sqlite 两个提供方。SQLite 用单调递增的 SCHEMA_VERSION；预览期 SESSION_FORMAT_VERSION 停在 0，不作任何兼容承诺，后端直接拒绝旧的磁盘格式。

可替换性的单位

能力 seam：三个角色，缺一不成立

Service Definition

声明接口的那一个

拥有自己的 ctx.<key> 与词汇类型。可以是抽象类，也可以是具体注册表 —— 但绝不是 TypeScript interface。

dsh-shell
→ ctx.shell / ShellExecutor
Service Provider

实现它的那一批

可以有多个。换掉它，就换掉了这项能力的实际执行世界，而消费方一行不改。

dsh-bash-local
dsh-bash-sandbox
（Windows 侧：dsh-pwsh-*）
Consumer

使用它的那一批

通常是面向模型的工具。它 inject 服务，因此对提供方的差异完全无感。

dsh-tool-bash
→ 模型看到的 bash 工具

规约里的硬话

seam 是完整的能力，永远不是其中某一个角色。添加一项能力意味着把三者一并设计；只写了个 provider 不叫加了 seam。角色通常各占一个包（当它们独立演化时），但一个包也可以同时承担多个角色。

为什么不用 interface

因为 seam 要在运行时被查找、被替换、被卸载。TS interface 编译后什么都不剩，无法承载 ctx 键、生命周期和可逆注册。这条规矩把"可替换"从文档承诺变成了类型系统事实。

杠杆

换一个提供方，为什么能改变整个产品

共享执行世界

文件系统与进程提供方共享同一个"执行世界"。于是 —— 把它们指向远程沙箱，也就把 Bash、PTY 和 LSP 一并搬了过去，无需任何提供方专用的 fork。

仓库里的 packages/e2b 就是这个 POC：sandbox + FS/subprocess 适配器，三个包换掉整台"机器"。

同一接口，差异可以非常大

subagent 提供方在同一个接口之后千差万别：从新建一个子 agent，到把一个轮次直接委派给另一个产品（Claude Code / Codex）。消费方那边只是调了同一个方法。

但边界也划得很清楚

容器、microVM、远程执行不是 ctx.sandbox 的提供方，而是整条能力 seam 的兄弟实现。—— 这类"什么算 provider、什么算另一条 seam"的判断，决定了插件架构会不会退化成"什么都能插，于是什么都插不准"。

反面教训在仓库里也有：docs/postmortem/ 有四篇复盘，其中一篇专讲 ACP 的默认导出把 inject 丢了，另一篇讲 !!js 表达式意外禁用了整组文件系统工具 —— 组合式架构的失败模式，往往是"某一层静默地什么都没装上"。

一个很能说明这个项目性格的细节

docs/tool-catalog.md 是生成的，而且生成器真的会把每个工具插件 boot 到一个真实 context 上，再读 ctx.tools.schemas() —— 因为工具 schema 静态不可知（运行时展开的枚举、拼接的描述、配置驱动的名字、原始 JSON-Schema 的 MCP 工具）。还有一道完整性守卫会 glob packages/*/tool-*，任何新工具没被登记进生成器清单，构建就失败。

值得单独讲

Code Mode：把 N 次工具往返压成一段程序

它不是"又一个工具"

run_code 由工具注册表自己拥有，是一条位于可过滤能力层之外的保留传输通道。在 mode: code 下，它是注册表唯一的 wire 贡献。

其他能力去哪了

变成提示词里一段生成的 SDK 声明（用当前运行时的语言写）。程序通过绑定去调它们 —— 每个嵌套调用会重新进入完整的受把关工具流水线，并链接回外层结果。

并发有明确契约

提交顺序决定启动顺序与策略；并发安全的调用体最多重叠到 maxParallelSubCalls。

// 模型写的是程序，不是一串 tool_call
const files = await fs.glob("src/**/*.ts")
const hits  = await Promise.all(
  files.map(f => fs.grep(f, /TODO/))
)
return hits.filter(h => h.length)

Code Runtime 也是一条 seam

ctx.codeRuntime 跑一段模型写的程序，对接宿主提供的异步绑定，并报告它打印了什么、返回了什么。后端按执行基底与源语言区分，两者都是服务上的只读描述符。

默认提供方跑在 worker thread 里。CodeRunRequest 严格遵守"边界上显式优于隐式"：时间预算、输出上限是实现的受校验配置，不是 run() 里藏一个 ??。

委派

Subagent：唯一允许多提供方并存的 seam

它和别的 seam 不一样：多个提供方按名字同时存在于一个 context 里（ctx.subagents），follow 的是 LLM 适配器注册表的模式，而不是单例 bash executor。

进程内

dsh-subagent-spawn-in-process
dsh-subagent-fork

新建子 agent，或从当前会话 fork 一份。

跨协议

dsh-subagent-acp
dsh-subagent-dsh-sdk

通过 ACP 或 JSON-RPC SDK 驱动另一个运行时。

跨产品

dsh-subagent-codex
dsh-subagent-claude-code

把一个轮次直接委派给别家的编码 agent。

两类能力，两种发现方式

start-time 能力写在静态描述符上（outputSchema / depthLimit / toolFilter …），服务在 run 存在之前就检查。
continuable（可续跑）子 agent由续跑管理器自己组装，因此只由一个可选方法把关：prepareContinuable —— 方法存在与否本身就是能力，用 TypeScript 收窄作为发现机制。

不支持就大声失败

请求用到提供方没有的能力，直接 SubagentError('UNSUPPORTED_CAPABILITY') 拒绝，绝不"接受了再静默忽略"。这条"fail loud, no silent degradation"贯穿全仓库 —— 在一个什么都能换的架构里，静默降级是最贵的 bug 类别。

长任务策略

Goal / Ralph / Workflow：都是策略，不是循环改动

Goal · 同会话的持久目标

挂在已有会话上的一个持久完成目标，带 active / paused / blocked / complete 相位与轮数上限。它是状态，不是调度器、也不是另一段对话；会话日志仍是唯一真相。

安全设计：创建、编辑、暂停、恢复要求"直接人类根权限"；而 goal 激活状态刻意不进持久回放 —— 所以 resume 与 fork 之后，必须由人再授权一次才能自动继续干活。

Ralph · 每轮都换一个新脑子

朝一个不可变目标推进的前台工作流：每一轮开一个全新子会话，不带父会话或前一轮的对话种子。

跨轮状态只靠两样东西传递：共享的 workspace，以及一份有界的结构化 handoff（status / summary / evidence / next steps / blocker）。handoff 是补充，不取代 workspace 的权威地位。

—— 一个明确对抗上下文腐化的设计。

Workflow · 确定性编排

ctx.workflowEngine 的默认提供方跑在 worker thread 里；脚本派生的子 agent 由调用方 agent 作父。

加上 packages/schedule（schedule_create 等三个工具，只在 opt-in 后、且只在插件加载之后创建的 root agent 作用域里注册），构成"让 agent 安排未来工作"的那一层。

三者的共同点：都建立在已有原语（workflow + subagent + 会话）之上，没有一个动了 agent-loop。规约里那条 Plugins, not loop changes —— 改 agent-loop 必须同时更新 docs/architecture.md —— 让"改循环"变成一件需要交代的事。
安全

沙箱：只管文件效果，且把"没管住"如实上报

SandboxMode含义
read-only请后端拒绝写入 —— POSIX 运行器额外放行 shell 必需的 /dev/null 汇；Windows ACL 运行器不授予任何可写根，并报告部分执行
workspace-write允许写入 workspace 根目录，以及后端承诺的临时区
danger-full-access绕过约束 —— 此模式下消费方根本不调用 ctx.sandbox，直接 spawn 原始 argv

划界写得很克制

网络与进程可见性不在这套词汇里。不承诺就不写进类型 —— 比含糊的"沙箱化"三个字有用得多。

三个平台后端

Linux  bwrap / Landlock
macOS  Seatbelt
Windows ACL 受限令牌

由 dsh-sandbox-local 提供；dsh-bash-sandbox / dsh-pwsh-sandbox 消费。

enforcement 是被上报的事实

full = 后端管住了该模式承诺的每一项文件效果；partial = 只管住了一部分（老 Landlock ABI、Windows 的 Everyone / 硬链接边界）。需要绝对承诺的消费方必须拒绝执行，或把这个区别暴露出来。

它已经咬过人一次

docs/postmortem/0004：Landlock 的 partial 通知把子进程失败误分类了。—— 把"部分执行"做成一等公民的类型，正是因为它在现实里真的会发生。

审批是另一层：packages/interaction 提供 approval / permission / ask-user 能力。当某个操作在当前权限策略下需要审批时，Web UI 会先问你 —— 沙箱管"能不能做到"，审批管"该不该做"。
进阶能力

Skills，以及让 agent 改自己

Skills：分层合并的目录

ctx.skills 跨 host 层 + 每个 scope 层合并提供方目录：仓库插件落到全局层，由 agent preset 的常驻组合挂载的插件落到该 preset 的层。读取时最近的层直接赢下同名冲突，同层内才按 rank → 提供方顺序 → 本地顺序裁决。

发现缓存按解析后的 scope 链做键，所以重新挂父（比如空会话重组）不需要改动注册表，下一次读取就能看到。

skill 是可选指令，不是会话事件 —— 所以它的词汇不住在核心里。

自我修改：刻意不装

cordis_define / cordis_run / cordis_inspect_* 让 agent 检查并挂载自己的插件，运行中的包还能继续注册新的模型可见工具，直到被 stop / undefine 或重启。

它不在任何发行树里。仓库注释写得很直接：动态包代码会真的进到实际运行时 —— 所以这是一个刻意的 opt-in，配套 dsh-cordis-host-runner 提供定义注册表与 vm 沙箱，组合里缺了它，这些工具根本不会激活。

仓库还带一个 pnpm run demo:cordis 演示："agent 修改自己的运行时"。

Extensions：比工具更重的一层

让 agent 定义带版本的 Cordis 包，运行其 host 与 browser 两半，并在写代码之前查询已批准的运行时元数据（ctx.cordisInspect 同时管 Host 与 Client 两侧的提供方目录）。—— 也就是说，agent 可以给 Web UI 自己加界面。

怎么读这件事

一个后来者最贵的成本是生态迁移。dsh 的选择是：把已有生态的配置资产（hook、skill 目录、MCP server、甚至整个竞品 agent）当成可挂载的层，而不是要求你先搬家。这和"一切皆插件"是同一条逻辑往外延伸 —— 插件边界既对内也对外。

反过来说：这也意味着 dsh 的差异化不在"工具更多"，而在那棵树本身可以被你重写。如果你只想要一个开箱即用的编码 agent，这个卖点对你没有价值。

一条容易踩的参数规则

启动器只解析自己的 flag，之后的一切都交给被启动的 profile。所以启动器 flag 必须写在最前面；第一个启动器不认识的 token，标志着应用参数的开始。

dsh --profile web --port 8080     # --port 属于 web 应用
dsh --profile web --help          # web 应用的 flag
dsh --help                        # 启动器自己的 help
最值得学的部分

工程纪律：一切皆插件的对价

插件架构最常见的死法是"能插但没人敢动"。这个仓库把约束几乎全部变成了可执行门禁。

覆盖率

packages/*/*/src 逐文件 100%。而且明确写着：test:coverage 才是 CI 门禁，不是 test。

快照 = 组装后的应用 transcript

每个非平凡的、模型可见或用户可见的行为变化，必须在同一个 PR 里、通过一个真实可运行的 example 补一条 keyless 快照。包级测试、e2e 断言、mock fixture 都不能替代它。

文档即门禁

doc-sync 校验一整批生成产物的新鲜度：工具目录、Cordis API 目录、配置目录、能力图、事件映射。文档漂移会让构建失败。

Agent Notes

非平凡改动必须在同一 PR 附一篇设计笔记，只有机械/局部编辑豁免。归档笔记冻结 —— 不得编辑，也不得当作现行权威。

不变量断言"拥有的关系"

运行时不变量检查权威事件流或可变数据，而不是"某个服务/方法存不存在"、插件元数据或固定的纯示例。没有可信关系时，一个"被解释过的空伴生物"就是正确答案。

在类型化边界上信任 TypeScript

不要为静态接口已经保证的值加运行时校验或兜底。只在这些地方校验：parser/config、队列、模型/工具 JSON、持久化/文件、worker、进程、wire。strict + noImplicitAny，每个残留的 any 要解释为什么无法收窄。

还有一条很有意思的写作规约：注释与文档只写完整契约与上下文，不写推理过程。写 contract、boundary、shape 之前先问有没有更精确的词 —— 该写 response fields 就别写 response shape。contract 一词保留给"调用方真正依赖的义务"。

你想做的事机制
添加模型提供方在 ctx.llm 上注册其适配器
添加面向模型的能力在 ctx.tools 上注册；其 schema 加入提示词组装

添加持久化终端执行注册 ctx.terminals 后端 + dsh-tool-terminal
添加用户命令（斜杠命令）在 ctx.commands 上注册；它无需模型轮次即可分派
添加后台工作在 ctx.jobs 上注册；job_* 工具负责收集或停止
限制所启动的进程使用 ctx.sandbox 后端；消费方在启动进程前包装 argv
拦截请求、工具或轮次用对应的 agent/* 或 tools/* 事件；agent/turn-stopping 会停止轮次
添加模型可见上下文调用 agent.inject()；它会落到下一次获准的请求中
添加 UI 或编辑器集成驱动 ctx.agents，并从 session/event 渲染
添加持久会话状态扩展 SessionEventMap；从日志渲染和回放
将注册项限定到单个 agent使用该 agent 的 agent.ctx
这张表本身就是架构的验收标准：如果你的需求在表里找不到落点，说明要么你在做的事应该变成一条新 seam，要么你真的需要改循环 —— 而改循环必须同步更新架构文档。

现状：开发者预览，别当生产依赖

明确写着"未来将出现破坏兼容性的变更"。AGENTS.md 里那条预发布姿态更直接：foundation over blast radius —— 没有外部消费者时，优先要正确的地基，可以自由重命名与重新分包，后端直接拒绝旧的磁盘格式。

适合谁

想深度定制 harness、想把 agent 能力接到自有执行世界（远程沙箱、内部工具、私有模型）、或者正在设计自己的插件式 agent 架构想找一份完整参考实现的团队。

暂不适合谁

需要稳定 API 的生产集成；只想要一个开箱即用编码助手的个人用户 —— 那部分它做得不错，但那不是它的差异点。
